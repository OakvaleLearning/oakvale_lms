## Catalogue: Programme → Module → Topic → Lesson

- `Module` is the top level of a programme (e.g. Foundation / Professional): tiers unlock modules (`TierModule`), and prerequisites and `sequential` are per module. `Topic` groups lessons inside a module. These were called Course and Module before November 2026 (migration `20261101120000_module_topic_rename`).
- Never name a local variable `module` (Next's lint rule forbids it, and it shadows Node's global); use `mod`.
- The mobile API keeps the old names alongside the new ones for older app versions: `/api/v1/courses/...` (legacy outline), `programs[].courses`, `continueLesson.courseSlug/courseTitle`, and `lesson.course` / `lesson.moduleTitle` (the topic's title) in `/api/v1/lessons/[id]`. New fields: `/api/v1/modules/...`, `programs[].modules`, `lesson.module`, `lesson.topicTitle`. Don't remove the old ones until the app no longer reads them.
- Certificates are per programme (`src/lib/lms/certificates.ts`): one is issued when a learner has completed every published module their active tiers unlock in the programme and their quiz average across those modules reaches `Program.certificatePassMark`. Certificate settings (on/off, template, pass mark, CPD) live on `Program`. `Certificate.scope` is the sorted module IDs covered; a learner who upgrades and finishes more modules gets a new certificate with the wider scope. Module certificates issued before November 2026 (`moduleId` set, `scope` null) stay valid, and no new ones are issued.
- Certificate templates use `{module}` (the titles of the modules covered, joined) and `{programme}`; `{course}` still works as an alias of `{module}`. `/admin/courses/:id` redirects to `/admin/modules/:id` (`next.config.ts`).

## Lessons are built from parts

- A `Lesson` holds ordered `LessonBlock`s ("parts"): VIDEO, AUDIO, DOCUMENT, TEXT, EMBED, SCORM, HTML, QUIZ.
- EMBED parts show a page hosted elsewhere (built for Genially) in a sandboxed iframe (`EmbedFrame`). The https URL is stored in `LessonBlock.body`, cleaned by `normalizeEmbedUrl` in `blocks.ts`, which accepts a share link, an `<iframe>` code or Genially's `<div class="genially-embed">` code. Learners mark them complete by hand. The mobile API reports them as `kind: "web"` so the app opens them through the existing WebView launch (`/m/lesson`). `Lesson.type` and `durationSec` are derived (`syncLesson` in `src/lib/lms/lesson-parts.ts`); one part means that part's type, several means `MIXED`. Never set them by hand.
- Part kinds, upload rules and labels live in `src/lib/lms/blocks.ts`; readiness (ready/processing/failed/empty) in `src/lib/lms/readiness.ts`.
- Progress is per part (`BlockProgress`) and rolled up to `LessonProgress` by `recordProgress` in `src/lib/lms/progress.ts`. Completion is sticky: adding a part never un-completes a learner. QUIZ and SCORM parts report their own result; all other parts use the client "complete" call.
- Question types: SINGLE, MULTIPLE, TRUE_FALSE, FILL_BLANK. Admins type fill-in-the-blank sentences with answers in `[brackets]` (alternatives split by `|`); `questionSchema` stores the prompt with `{{blank}}` markers, `options: []` and one `correct` entry per blank. Helpers and the lenient answer matching live in `src/lib/lms/fill-blank.ts`; each blank earns its share of the question's points.
- A lesson can have at most one SCORM part and one QUIZ part. A final assessment (`Quiz.kind = EXAM`) must be the lesson's only part. It is listed last and opens once every other lesson is complete. `Quiz.optional` (EXAM only) lets learners skip it: filter with `requiredLesson` (`src/lib/lms/access.ts`) wherever module completion or progress is counted; its score joins the certificate average only once taken.
- DOCUMENT parts are always viewed in the lesson (PDF and images directly; Word/PowerPoint/Excel through Microsoft's embed viewer, `officeViewerUrl` in `blocks.ts`, which fetches a short-lived signed URL). `LessonBlock.allowDownload` (default true) controls the Download / Open-in-new-tab buttons only: when false the page never generates an attachment link. It deters casual saving and is not DRM; the signed view URL is still in the page. Toggle: `src/components/admin/DocumentAccess.tsx`.
- Files attach to a part (`ContentAsset.blockId`), not to the lesson. Read `lesson.blocks[].asset`; `lesson.asset` no longer exists.
- Admin editor: `src/app/admin/lessons/[id]/` (server actions in `actions.ts`, client builder in `src/components/admin/LessonBuilder.tsx`). Learner view: `src/components/learn/LessonParts.tsx`. Mobile API: `/api/v1/lessons/[id]` returns `parts[]` (plus `content` for older clients).
- Changing the schema: write a Prisma migration by hand only if `prisma migrate dev` can't run; run `npx prisma generate` before type-checking.

## Quizzes show one question at a time

- `QuizPlayer` (lesson quizzes and final assessments) shows one question at a time. Untimed, learners can go back and forth (Previous/Next and numbered buttons) before submitting. With `Quiz.secondsPerQuestion` set, there's a Start screen, each question has a countdown, there's no going back, it moves on at zero, and the last question submits what's answered. After submitting, learners step through their results. Lesson-quiz timing is enforced in the browser only (`/api/lms/quiz` grades a whole submission); pre-assessment timing is enforced on the server. The mobile API passes `secondsPerQuestion` for the app to honour.

## Pre-assessments gate enrolment and access

- A tier can have a `PreAssessment` (an entry test). While it is `enabled` and its question banks hold at least one question (`activeAssessmentWhere`), it gates two things:
  - **Checkout for that tier.** `/api/enroll` checks `needsPreAssessment` and returns `{ preAssessment: "/pre-assessment/<tierId>" }`, which `EnrollButton` follows.
  - **The tier's modules, wherever they're sold.** `getModuleAccess` (used by `getUnlockedModuleIds` / `getModuleLock`) keeps a gated tier's modules locked (`ModuleLock` "PRE_ASSESSMENT") in that tier and in any bigger tier containing all of them, e.g. Professional inside Full Programme. A smaller tier that shares a module (Foundation) isn't affected. Locked modules still show on `/learn` with a "Take the pre-assessment" link, and `offerings` counts them as bought.
- `Enrollment.preAssessmentWaived` skips the gate. Admins set it with "Skip pre-assessment" when granting a tier, or "Waive / Require pre-assessment" on `/admin/learners/[id]`. Admin grants no longer skip by default. The `proctored_pre_assessments` migration waived every enrolment that was ACTIVE at the time (grandfathered). The mobile API has no checkout, but module locks apply there too.
- Questions live in reusable `QuestionBank`s (`BankQuestion`, same shape and the same four types as a lesson quiz's `Question`). A pre-assessment uses one or more banks (implicit m2m). Each attempt draws `questionCount` questions when it starts and stores their ids on `PreAssessmentAttempt.questionIds`.
- **One question at a time, no going back.** The server sends only the current question (`PreAssessmentAttempt.position`, see `getOpenAttempt` / `advanceAttempt`). Answers to earlier questions are locked: check-ins autosave only the current one, and the "advance" action ignores answers for any question but the current one. With `secondsPerQuestion`, each question has its own countdown (`questionStartedAt`). `clock()` moves the attempt on when it runs out (+5 s grace), even with the tab closed; late answers are ignored, and if every question runs out the attempt ends `TIMED_OUT`.
- **No repeats:** a draw excludes every question the learner has been shown in any pre-assessment attempt, including reset and voided ones. When fewer unseen questions are left than `questionCount`, the status is "no-questions" and no attempt can start; the admin page shows how many attempts the banks allow (`pool / questionCount`). The draw is spread evenly across banks (`drawEvenly`): 40 from 10 topic banks = 4 each.
- **Proctoring** (settings on the assessment: `timeLimitMinutes`, `proctored`, `maxStrikes`, `webcam`; event catalogue in `src/lib/lms/proctoring.ts`):
  - The time limit is enforced on the server via `deadline` (+30 s grace). Late answers are ignored, and expired open attempts are closed as `TIMED_OUT` on the answers autosaved before the deadline.
  - The player (`PreAssessmentPlayer.tsx`) requires full screen (skipped where the browser can't, e.g. iPhone), blocks copy/paste/context menu/print and dev-tools keys, and checks in every 15 s at `POST /api/pre-assessment/activity` (autosave plus events, `keepalive` on page hide).
  - Strikes: leaving the page, switching window, leaving full screen, copy/cut/paste, camera off, and a second window, device or reload (a different `clientId`, detected on the server). On `maxStrikes` strikes the attempt ends as `TERMINATED`, always a fail.
  - Webcam: camera required, with a still about every minute to `POST /api/pre-assessment/snapshot`, stored in the bucket under `proctoring/<assessmentId>/<attemptId>/` (`PreAssessmentSnapshot`). The camera isn't required when storage isn't configured. The dev environment shares the production bucket.
  - Check-ins, submits and timeouts lock the attempt row (`SELECT … FOR UPDATE` in `withAttempt`), so they never interleave.
  - All of this deters casual cheating; it can't stop a second device or someone in the room. That is what the stills and the review page are for.
- Admin: `/admin/tiers/[id]/pre-assessment` (settings, attempts list, Reset) and `/admin/tiers/[id]/pre-assessment/[attemptId]` (webcam stills, proctoring log, answers, "Cancel result"). Reset sets `resetAt` (attempts stop counting but stay on record). Cancelling sets `voidedAt` and `passed = false`, which re-locks any modules it opened.
- Retakes: `maxAttempts` (null = unlimited) counts every attempt not reset; `retakeAfterHours` is the wait after a failed one. A pass never expires and is per tier.
- Foundation bank seed (200 questions, one bank per topic, from `Oakvale_Foundation_Question_Bank_Refined_Context_and_Ethics.xlsx`): `prisma/data/foundation-question-bank.json`, loaded by `npm run seed:question-banks` (needs `DATABASE_URL`). It only adds: banks match by title, questions by ID or wording. The question ID, difficulty, critical-safety tag and blind spot are kept in each explanation, which learners never see.
- Code: logic `src/lib/lms/pre-assessment.ts`; learner page `src/app/(checkout)/pre-assessment/[tierId]/` (adds an "Assessment" step to `CheckoutSteps`); admin actions `src/app/admin/question-banks/actions.ts`; banks at `/admin/question-banks`. Marking is shared with lesson quizzes (`gradeAnswers`, `toLearnerQuestion` in `src/lib/lms/quiz.ts`), as is the answer UI (`QuestionCard`). `QuestionEditor` takes a bound `save` action.

## Admin activity log

- **Every admin operation must record itself.** After a change succeeds, call `audit(admin, "<area>.<verb>", summary, { target, details })` from `src/lib/audit.ts`, where `admin` is the session returned by `requireAdmin()`. Write the summary in plain English with names, not ids (e.g. `Updated tier “Foundation” (Child Care): price ₦30,000 → ₦35,000`). For edits, put `changes(before, after)` in `details`; replace long text fields with `["…", "(changed)"]`. The prefix before the dot decides the category (`AUDIT_CATEGORIES`), so a new area needs a prefix there.
- Covered today: everything in `src/app/admin/**/actions.ts` and the `*-actions.ts` files, the admin support API, the CPD CSV export, community moderation (announcements, removing others' posts and comments, pin and lock, group admins, banners), and admin sign-ins plus failed password attempts on admin accounts (`/api/auth/login`). Presigning an upload isn't logged; finishing it is.
- `audit()` never throws (failures go to the server log), and rows are never edited or deleted. The actor's name and email are copied in (`actorId` is set to null if the account goes). The IP comes from `clientIp()`.
- Page: `/admin/activity` (filter by admin, category, Lagos-time dates, search, or `?target=type:id`; learner pages link to it). CSV: `GET /api/admin/activity` with the same filters. Filters are in `src/lib/audit-query.ts`.
- Nothing was logged before the `admin_audit_log` migration. That migration backfills only what existing rows attribute to a person (support replies, created events, announcements), marked `{"recovered": true}`. Earlier admin grants, certificate revocations and team changes can't be attributed.

## Oakvale Guide (app-navigation assistant)

- Separate from the lesson tutor. The tutor (`src/lib/lms/tutor.ts`, `TutorPanel`) answers questions about a lesson's content; the Guide answers "where is / how do I" questions about the app and plays step-by-step walkthroughs. Each prompt sends the other's questions across. Keep them apart: the Guide opens from "Help & guide" in the sidebar (and a compass icon in the mobile top bar) and slides in from the left, never as a floating button, so it can't cover the tutor's bottom-right launcher.
- Walkthroughs live in `src/lib/guide/walkthroughs.ts` (admin and learner sets, chosen by `session.role`). Steps target the screen, not the code: a sidebar link by href (`data-guide-nav` in `DashboardShell`), or a button/link/heading by its visible label (`{ text, closest? }`). **Renaming a button, panel title or page heading can break a walkthrough step; update the walkthroughs with it.** `checkpoint` steps let a tour start partway when the user is already on that page.
- The tour overlay (`src/components/guide/GuideTour.tsx`) is mounted in `DashboardShell` and the checkout layout; state is in sessionStorage (`src/components/guide/store.ts`) so tours survive navigation. The dimming never blocks clicks.
- API: `POST /api/guide` (`src/lib/guide/assistant.ts` builds the prompt with a per-role app map; update the map when pages change). The model can only offer a walkthrough through the `show_walkthrough` tool, whose ids are an enum. Conversations stay in the browser (no DB tables); limited to 40 messages an hour per user via `rateLimit`.

## Community groups and group admins

- Group membership is derived, not stored (`src/lib/community/access.ts`): an active enrolment matching the group's audience plus a verified email. Site admins (`User.role = ADMIN`) are in every group and show as the Oakvale Team.
- A `GroupAdmin` row makes one member a moderator of one group only; it grants nothing in `/admin`. Group admins are always members of that group, paid or not (`getMemberGroups` and `groupMemberWhere` include them).
- Group-scoped moderation goes through `canManageGroup(viewer, groupId)` (site admin or `GroupAdmin` row) and `managedGroupIds(viewer)`: announcements, pin and lock, removing any post or comment, and appointing or removing group admins (`setGroupAdmin` in `src/app/community/actions.ts`, button in `src/components/community/GroupAdminToggle.tsx`, shown on the group's Members tab). Never check `session.role === "ADMIN"` for these; use the group-scoped helper.
- Still site-admin only: creating events and uploading event images, "Manage group", and the `/admin` area.
- `groupMemberWhere`, `groupLearnerWhere` and `notifyGroup` need the group's `id` as well as its audience fields.
- The group banner (`src/app/community/[group]/page.tsx`) is the themed blue gradient unless the group has a `coverImage`. Group admins and site admins get a "more" (…) menu on it with Add/Change/Remove photo (`GroupCoverButton`, actions `createGroupCoverUpload` / `saveGroupCover` in `src/app/community/actions.ts`) that uploads straight to the bucket under `covers/groups/<id>/`. The admin-only `CoverImageField` in `/admin` writes the same field.

## Theme

- The visual theme is copied from the main site (`OakvaleLearning/oakvale_main`: `app/globals.css`, `tailwind.config.js`, `app/layout.tsx`). All tokens live in `@theme` in `src/app/globals.css`; fonts are loaded in `src/app/layout.tsx` with `next/font/google`. Change colours or fonts there, not in components.
- Colours: `primary-*` is forest green (600 = the main site's forest-mid `#145c3f`, 800 = forest `#0a3d2b`, 200/100 = mint/mint-light, 400 = sage). `gold` and `gold-light` (`#c8881a`, `#e8a832`) are for highlights. `accent-*` is the error red (700 = the main site's `#9a1d1d`), so keep using it for errors and warnings, not decoration. `ink-*` are warm greys (900 = charcoal `#1c1c1c`), `canvas`/`cream` is `#f7f3ec` and `line` is `#e8e4de`.
- Fonts: DM Sans for the interface (`font-sans`, the default), Cormorant Garamond for page titles and key figures (`font-display`, or `font-heading`), EB Garamond for lesson reading text (`font-serif`, used by `.lesson-md`), Geist Mono for code.
- Hex values that can't use tokens (emails in `src/lib/email-templates.ts` and `src/lib/community/emails.ts`, `src/app/manifest.ts`, the viewport `themeColor`, certificate defaults in `src/lib/certificate-design.ts`, swatches in `TemplateEditor.tsx`) use `#145c3f`. Update them together if the primary colour changes. Existing saved certificate templates keep the colours they were saved with.
